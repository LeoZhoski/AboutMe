# AI 架构师笔记 (AI Architect Notes)

## 概述

这个文件夹包含 AI 生成代码的架构说明和修改指南，解决代码逻辑透明度问题。

当 AI 生成代码时，用户往往只能看到功能界面，但对背后的数据库设计、权限控制、核心业务逻辑等关键架构处于"黑箱"状态。当代码的逻辑无法通过视觉直接验证时，用户（尤其是低频编程者或产品经理）就失去了对系统的掌控感和信任感。

## 目标

- **理解架构**：清晰说明 AI 的设计思路和实现逻辑
- **掌握决策**：记录系统的关键技术决策和设计原因
- **指导修改**：提供具体的修改和扩展指导
- **避免风险**：预防技术债务和安全隐患

## 文件夹结构

### 1. 数据与状态 (`1_data_and_state/`)
定义数据存储、传输和管理的架构
- `data-model.md` - 统一数据模型设计（包含 Airtable 字段定义和类型定义）
- `api_contracts.md` - 前后端数据交换协议
- `state_management.md` - 前端状态管理方案
- `domain-mapping-functions.md` - 个人能力提升三级映射函数

### 2. 权限与安全 (`2_security/`)
用户身份验证和权限控制机制
- `authentication.md` - 用户身份验证流程
- `authorization.md` - 权限控制和访问管理

### 3. 核心业务逻辑 (`3_business_logic/`)
应用核心功能的实现逻辑
- `payment_flow.md` - 支付业务流程
- 其他关键业务流程...

### 4. 配置与环境 (`4_configuration/`)
应用配置和环境管理
- `env_variables.md` - 环境变量配置说明

### 5. 外部依赖 (`5_dependencies/`)
第三方服务和库的集成
- `key_libraries.md` - 核心第三方库说明

## 使用指南

### AI 开发助手
每次生成或修改代码后，同步更新对应文档：
- 实现用户登录功能 → 更新 `authentication.md`
- 修改数据模型或字段 → 更新 `data-model.md`  
- 添加支付功能 → 更新 `payment_flow.md`
- 调整分类体系 → 更新 `domain-mapping-functions.md`
- 修改 API 接口 → 更新 `api-contracts.md`
- 更改状态管理 → 更新 `state-management.md`

**重要**：在更新前先检查是否已有相关文档，避免创建重复文档。

### 项目管理者
- 了解功能实现方式 → 查看对应文档
- 评估新功能可行性 → 参考架构说明
- 问题排查定位 → 根据文档找到相关代码

### 技术维护人员
- 修改现有功能 → 先阅读文档了解逻辑
- 添加新功能 → 参考现有架构模式
- 性能优化 → 根据文档识别关键路径

## 文档规范

### 内容要求
- **功能说明**：清晰描述功能作用和实现方式，为代码增加足够的注释来实现自然语言的阅读体验
- **设计原因**：解释技术选型和架构决策
- **修改指导**：提供具体的修改步骤和注意事项
- **风险提示**：标明潜在风险和限制条件

### 格式要求
- 使用清晰直接的技术语言
- 为关键代码提供详细注释
- 包含完整的代码示例
- 提供具体的操作指导

### 🚫 文档重复性约束（重要）

为避免文档重复和维护困难，严格遵守以下约束：

1. **单一数据源原则**
   - 每个技术领域只维护一个权威文档
   - 避免在多个文档中描述同一功能的不同方面
   - 相关内容通过引用链接组织，而非重复描述

2. **文档职责边界**
   - `data-model.md`: 数据结构、字段定义、类型系统
   - `api-contracts.md`: API 接口、请求/响应格式
   - `state-management.md`: 状态管理策略、数据流
   - `domain-mapping-functions.md`: 业务逻辑函数、映射关系

3. **禁止创建重叠文档**
   - 不创建只描述某一方面细节的文档
   - 不为同一数据源创建多个定义文件
   - 不将配置信息分散在多个文档中

4. **文档组织原则**
   - 按技术层次组织，而非按功能点
   - 上层文档引用下层文档，反之则不行
   - 横向关系通过明确的引用链接建立

5. **新增文档检查清单**
   在创建新文档前，必须确认：
   - [ ] 内容不与现有文档重复
   - [ ] 有明确的职责边界
   - [ ] 符合整体文档架构
   - [ ] 必要时更新了相关文档的引用

### 违反约束的后果
- 文档不同步导致误导
- 维护成本倍增
- 用户困惑和信任度下降
- 技术债务累积
